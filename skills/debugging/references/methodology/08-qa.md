# Phase 8: Real-Surface QA

Exercise the exact user-visible path that originally failed.

| Product | Required surface |
|---|---|
| CLI or TUI | Run the installed command interactively; capture exit code, stdout, stderr, and side effects |
| HTTP API | Start the real service and call the exact endpoint with a suitable client; inspect status, headers, and body |
| Browser app | Drive a real browser with the available standards-based automation; capture observable DOM, console, network, and screenshot evidence |
| Agent pipeline | Repeat the original input; capture messages, tool activity, result, and non-zero usage where applicable |
| Worker | Trigger through the normal queue, scheduler, or API path and observe completion plus side effects |
| Protocol server | Invoke through a real protocol client, including handshake |
| Native or bundled binary | Re-run the exact command and input; capture exit status, signal, and crash artifacts |
| Daemon | Start fresh and observe for at least the original manifestation interval, including resources |

Do not substitute a lower surface: an HTTP probe does not prove a browser flow; a direct function call does not prove a queue trigger.

Always check for semantic failure hidden inside apparent success: empty 2xx responses, error-bearing fields, zero usage, exception text with exit code zero, unobserved async failures, recovered panics, stale reads, completed jobs without side effects, or stale cache hits.

Record the scenario, exact invocation, bounded observed output, expected output, and verdict. Partial or regressed behavior returns the investigation to causal confirmation. Note unrelated silent-failure sites as follow-ups; do not expand the current fix.
